# ADR 0006: Site URL, no `base`, and llms.txt generation

**Status:** Accepted
**Date:** 2026-11-07

## Context

Three constraints interact:

1. Starlight **always** registers its own `@astrojs/sitemap` integration
   (verified in `@astrojs/starlight/dist/index.js`), and sitemap warns
   loudly when `site` is unset — so a warning-free build effectively
   requires `site`.
2. The `starlight-llms-txt` plugin (used to generate `llms.txt`,
   `llms-small.txt` and `llms-full.txt`) requires `site` because it emits
   absolute URLs.
3. `starlight-links-validator` 0.27.0 was observed to flag **every**
   internal link as invalid when `base` is set to a subpath (its page keys
   are built with the base prefix while content links stay root-relative),
   which fails the release gate.

The repository defines no docs deployment URL (its homepage is the GitHub
repository itself), so any canonical URL is an assumption that the
maintainer may need to change.

## Decision

- `site: "https://elcoosp.github.io"` — the GitHub Pages origin derived
  from the repository identity. All generated absolute URLs (sitemap,
  llms.txt, canonical) use the origin root because no `base` is set, so the
  value is a single coherent placeholder. **Assumption to revisit:** if the
  docs deploy elsewhere, change this one line.
- **No `base`** is set. This keeps `starlight-links-validator` green and
  keeps all content links root-relative. A subpath deployment would require
  setting `base` and re-validating the links-validator interaction above.
- llms.txt files are generated by the **`starlight-llms-txt` community
  plugin** (`plugins` entry in `astro.config.mjs`), producing `llms.txt`,
  `llms-small.txt` and `llms-full.txt` at the site root of every build —
  verified present in `dist/`.

## Single-locale configuration

`locales: { root: { label: "English", lang: "en" } }` with
`defaultLocale: "root"`, plus the **explicit `i18n` collection** in
`src/content.config.ts` (`i18nLoader()` + `i18nSchema()`) and a
`src/content/i18n/root.json` file. Without the explicit collection,
Starlight warns `The collection "i18n" does not exist or is empty` on every
build; with the root-locale pattern, no UI-translation work is required.

## Custom 404

`src/content/docs/404.mdx` is marked `draft: true`: Starlight's built-in 404
route picks the entry up through `getEntry` (which includes drafts) while
the dynamic `[...slug]` route generation excludes drafts in production —
so the entry customizes the 404 page without generating a conflicting
second `/404` route (which would warn `Could not render /404 ... as it
conflicts with higher priority route /404`). The draft banner Starlight
then renders on that page is hidden via the page's `head` frontmatter
style; see `docs/qa-report.md`.
